Executive Summary

What we did

  • Bit-level comparison of published vs. base model weights (Step 1)
  • Generated and graded base and edited on 100 problems each of GSM8K and MATH-500 (Steps 2, 7)
  • Compared with 3 controls that randomly change the same 64 columns (Steps 3, 5)
  • Checked test overlap and edit selection in author logs (Step 4)

Conclusions

  • Published model has only the 2-matrix, rank-1 edit described (Step 1)
  • GSM8K 31→70%, MATH 16→53% (Steps 2, 7). With authors' sampling order: 18→70%, 5→57% (8, 9)
  • 3 random-direction controls drop to 15–20% (Steps 3, 5)
  • No overlap between training problems and test (Step 4)
The edit doesn't add math skill; it "breaks reasoning loops". Score gap explained. Search reproducibility not confirmed.

1-1 What We Verified

Original study

  • "Sparks of Weight-Space Programming: LLMs can natively read & write neural network weights"
  • Rikiya Takehi, Jayden Teoh, Alex Zhang, Omar Khattab (MIT CSAIL), published 2026-11-02
  • 8 experiments on whether a general LLM (GPT-6 Astra) can read, fix and write network weights without training

Claim checked here (Experiment 8)

  • Astra directly edited just 0.016% of Qwen3.5-0.8B's weights
  • This raised MATH-500 7.9% → 48.1%, GSM8K 13.8% → 67.1%
  • Cause is "reasoning loops"; the edit removes that direction
Chosen because Experiment 8 has a published model and logs, and the smallest model, so it can be reproduced locally.

Until now
Weights are written by optimizers (SGD, Adam), purpose-trained networks, or compilers of formal programs

A general LLM reads and writes weights directly from a natural-language goal. No gradients, no training loop

1-3 History (1): Ways to "Write" Weights
YearWorkContent
1992Fast Weight Programmers (Schmidhuber)Origin of the idea of one network outputting another's weights
2016HyperNetworks (Ha et al.)A small network generates a large network's weights. The generator itself needs training
2017Software 2.0 (Karpathy)View that programs move from human-written code to optimizer-written weights
2021Linear Transformers = Fast Weight Programmers (Schlag et al.)Linear attention equals rewriting weights at run time (cited by the blog as a "purpose-trained writer")
2021, 2023RASP (Weiss et al.) / Tracr (Lindner et al.)Compile formal programs into Transformer weights (cited by the blog as a "compiler")
The "writer" was always an optimizer, a purpose-trained model, or a formal-language compiler. No general LLM wrote weights from natural-language instructions.

1-5 Why It Matters (Technical)

If true

  • Targeted fixes for specific defects with no training data or GPU training (0.016% edit)
  • Small change may avoid the forgetting common in fine-tuning
  • Fix explains which component is at fault, so it's built-in interpretability
  • A new self-improvement path: LLMs improving LLM weights

Which is why we check

  • Large score gains can depend heavily on eval settings (limit, sampling)
  • If "any change works", it may be chance, not AI understanding
  • Tuning on test problems would make gains illusory
  • One success alone doesn't make it a reliable method
Our 4 verification questions map one-to-one to the 4 concerns on the right.

2-2 The Problem Astra Found: Loops

Base model state

  • 85 of the first 96 training problems ran to the 32,768-token limit
  • ~95% of cut-off outputs end in a repeated 8-word sequence
  • Qwen's own model card warns it is "prone to reasoning loops"

Astra's diagnosis (50-pass run p50c)

  • Paired productive vs. repetitive continuations; took "repetition direction" u from residual diffs at layer 16, 20 outputs
  • Found MLP neurons writing that direction most (layers 15, 19; 64 each)
  • Confirmed strengths 1, 2, 4 lower only repetitive log-probs, then chose 64 columns, strength 6
So the edit didn't "teach math"; it "removed a habit of not stopping". This frames the whole verification.

3-12 Implementation issue: long generations in mlx-lm

Symptom

  • Generations near 32,768 tokens crash on Metal's resource limit (499,000)
  • mx.clear_cache() and splitting batches did not fix it

Cause and fix

  • ArraysCache.advance stacks left_padding −= N every step without evaluating, so the lazy graph for 18 linear-attention layers keeps growing (confirmed with mx.export_to_dot)
  • mx.eval each cache's left_padding, lengths, offset every 256 steps → graph stays at ~1,040 edges
Separately, competing with other apps for memory causes GPU out-of-memory stops. We save answers per problem so runs can resume (Step 7 at batch 24: no stops).

Confirmed

The article's 2-matrix, rank-1 edit: GSM8K 31% → 70%, MATH-500 16% → 53%. Random changes made it worse. No tuning on the test

What it does

It added no math skill; it broke reasoning loops so the model finishes. Accuracy on finished problems is unchanged
